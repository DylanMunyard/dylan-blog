## Proxmox LXCs
Proxmox is a virtualisation host. So you can deploy VMs on it, as well as Linux Containers (LXC). The second is what we'll use. 

Proxmox LXCs are the lightweight version of VMs. VMs are about emulation. They emulate the whole machine. 
Proxmox LXCs still run an operating system, but they are running directly on the host inside a namespace (cgroup). 

To create a LXC, you need a template to create it from. To do this, log in to Proxmox via the terminal (SSH or plug in a keyboard and monitor to the server).

### Download a template
Use `pveam` cli to install a template

```bash
pveam update              # refresh available template list
pveam available           # list all templates (add -section system for OS templates)
pveam download local <template-name>   # download to local storage
```

Install Debian
```bash
pveam available | grep debian
pveam download local debian-12-standard_12.12-1_amd64.tar.zst
```

### Deploy LXC
Log in to Proxmox (the URL is shown when you log in via the terminal — see [Part 2](/posts/building-a-home-server-pt2) for installing and logging in to Proxmox and finding the web URL).

- Expand `Datacentre` and your server will be listed there
- Right mouse-click your server node -> Create CT
- **Leave "Unprivileged container:" checked** — it's the default

![Proxmox right-click context menu showing the Create CT option on the server node](/assets/building-a-home-server-pt4/create-lxc.webp)

<Callout kind="info" title="What unprivileged means for your files">
An unprivileged container shifts every user ID by 100000. The apps run as user `1000` inside the LXC, which lands on
the host as `101000`, and the files on your ZFS pool owned by `1000` show up inside the LXC as `nobody`. We fix that
further down with an ID map that pins user `1000` inside to user `1000` on the host.
</Callout>

- Put in a password and click next. Then you need to choose a Template, this is basically what OS you'll run. 

![Proxmox CT template selection screen](/assets/building-a-home-server-pt4/choose-ct-template.webp)

- Choose the template you downloaded

<Callout kind="tip" title="Using a different distro">
If you're more familiar with another Linux distribution, download that template and use it to create your CT.
</Callout>

As you click through, you can tweak memory, CPU, storage. This is resource management, because it's virtual you're not actually
allocating that much memory, just how much the LXC will see. I tend to allocate the same memory and CPU as my host. 

This will create a new LXC, stopped by default. Now you need to start it. 
- Click it beneath the server node. 
- At the top right click Start
- Wait for it to start, it will have a green icon on the LXC under the server node
- Click Console
- Log in with `root` | `the password you set`

<Gallery items={[
  { src: "/assets/building-a-home-server-pt4/stopped-ct.webp", alt: "New LXC container listed under the server node, stopped by default" },
  { src: "/assets/building-a-home-server-pt4/console.webp", alt: "Proxmox console after logging in as root" },
]} />

You can spin up as many of these as you want to tailor your setup how you prefer. E.g. 
- 1 LXC per app
- 1 LXC for all the apps
- 1 LXC for the *arr apps, 1 LXC for the media server.

<Callout kind="tip" title="Splitting apps across LXCs">
If you don't care, run them all inside the same LXC, but as you grow more experienced, you may want to separate them 
into their own LXCs. The typical driver behind splitting them is resource constraints. Especially on 8GB, you might
want to have a 512MB LXC just for the *arrs, and a LXC with 6G and more CPUs for the media server.
</Callout>

### Give your LXC a static IP
Proxmox uses a virtual networking stack to give LXCs their own address space, and uses a bridge to make the LXCs accessible
from the host. That means you can access your LXC via an IP on your host network, e.g. `192.168.1.212`. 

Finding the host network IP can be tricky, it's not shown in the Proxmox UI. So its best practice to assign a static IP to your LXC
that comes from your home network. So if your home network is in the `192.168.1.*` range, assign a static IP `192.168.1.88`
and that is your LXC's IP. Find your home network range by running `ip a` (Linux) or `ipconfig` (Windows) to find your IP. 

In the Proxmox UI, select the LXC > Network > Edit the network device:

![Proxmox CT network device configuration screen](/assets/building-a-home-server-pt4/ct-networking.webp)

- Check IPv4: Static
- Enter `192.168.1.88/24` in IPv4/CIDR
- Gateway: `192.168.1.1`

Restart your LXC and it will come back online with that IP.

<Callout kind="tip" title="See it in action">
To see this in practice, run a simple web site within the LXC then access it from the static IP

```bash
mkdir -p /tmp/www && echo "OK" > /tmp/www/index.html
cd /tmp/www && python3 -m http.server 8000
```

Open `192.168.1.88:8000` from outside the LXC and it will show `OK`.
</Callout>

This is important, it sets up the building blocks for everything you'll need to run the media server. 

### Enable nesting, map the user IDs, mount the ZFS pool
Docker needs to do privileged things inside its own container — create nested namespaces and cgroups, mount overlayfs
for its storage driver, and use the kernel keyring. Proxmox gates those behind two container features, `nesting` and
`keyctl`. Switching both on is enough. AppArmor stays on.

Proxmox requires passing through mount points on the host to the LXC via explicit approval.

The ID map lines undo the 100000 shift for the two IDs the apps actually use, so user `1000` and group `1005` mean the
same thing inside the LXC as they do on the host.

1. Access the Proxmox host via terminal
2. Let root hand out those two IDs:
```bash
echo 'root:1000:1' >> /etc/subuid
echo 'root:1005:1' >> /etc/subgid
```
3. `nano /etc/pve/lxc/100.conf`
4. Use the arrow keys to select the last line, hit enter to create a new line
5. Paste the following
```bash
features: nesting=1,keyctl=1
mp0: /media-tank,mp=/media-data
lxc.idmap: u 0 100000 1000
lxc.idmap: u 1000 1000 1
lxc.idmap: u 1001 101001 64535
lxc.idmap: g 0 100000 1005
lxc.idmap: g 1005 1005 1
lxc.idmap: g 1006 101006 64530
```
6. Type `ctrl + o` then hit `Enter` to save
7. Type `ctrl + x` to exit

<Callout kind="warn" title="If a features line is already there">
`features:` can only appear once. If the file already has one, edit that line instead of pasting a second.
</Callout>

Each `idmap` line reads: starting at this ID inside the LXC, map to this ID on the host, for this many IDs. So users
`0-999` go to `100000-100999`, user `1000` maps straight to `1000`, and everything above carries on at `101001`. The
group lines do the same around `1005`. The three ranges have to add up to 65536 or the LXC won't start.

Reboot the LXC. It now mounts the ZFS pool at `/media-data`, and files the apps write there land on the host owned by
`1000:1005`.

## Running Apps
<Callout kind="info" title="From now on ..">
Run all of the following from within your LXC
</Callout>

Go with Docker for running apps. It's the best supported runtime for every app you'll need.

### Create a non-root user
<Callout kind="warn" title="Don't stay logged in as root">
The LXC is running root by default. The best practice would be to create a new user, and log in with them:
</Callout>

```bash
adduser dylan # just put in your name, ignore the rest
```

![Terminal after creating a new non-root user with adduser](/assets/building-a-home-server-pt4/addinguser.webp)

```bash
usermod -aG sudo dylan # give them sudo access
apt update && apt install sudo # install sudo command
exit # will log you out, log back in with the new user
```

### Install Docker
<Callout kind="tip" title="Same steps as installing on Debian directly">
Because your LXC is running Debian you can read the Debian docs for installing Debian, [here](https://docs.docker.com/engine/install/debian/)
</Callout>

```bash
# Add Docker's official GPG key:
sudo apt update
sudo apt install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Add the repository to Apt sources:
sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/debian
Suites: $(. /etc/os-release && echo "$VERSION_CODENAME")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update

sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl status docker
sudo docker run hello-world
```

The last step will probably fail, permission denied. You need to read 
[Linux post-installation steps for Docker Engine](https://docs.docker.com/engine/install/linux-postinstall/).

```bash
sudo groupadd docker
sudo usermod -aG docker $USER
exit # log out and back in again
docker run hello-world # should work now
```

### Set up a shared group for file permissions
<Callout kind="warn" title="Don't just run everything as root">
We're about to deploy the media server apps. They need to access the ZFS pool to read and write the media,
creating a shared user and group for the containers will solve file access issues.
</Callout>

1. Create a group on the LXC that all the apps will share:
```bash
sudo groupadd -g 1005 mediaapps
```
2. Add your own user to it too, so you can browse/manage the files yourself:
```bash
sudo usermod -aG mediaapps dylan
```
3. Hand ownership of the pool to that group, and set the setgid bit so anything created underneath it inherits the
group automatically. Run this one **on the Proxmox host**, against `/media-tank` — the top of the pool belongs to the
host's root user, and an unprivileged LXC can't change it. Use the number `1005` rather than the name, because
`mediaapps` only exists inside the LXC:
```bash
chgrp -R 1005 /media-tank
chmod -R 2775 /media-tank
```
The leading `2` in `2775` is the setgid bit — without it, new files created by a container would get that
container's own primary group instead of `mediaapps`, and you'd be back to permission errors.

<Callout kind="tip" title="Picking a PUID">
Any UID works as long as it isn't already used — the examples below use `1000`.
</Callout>

## Docker Compose
Docker compose lets you manage multiple containers declaratively in a single file `compose.yaml`. It has some handy features that make
it simple for the different apps to reach each other. 

To manage the compose file, you run `docker compose up -f compose.yaml` and it starts the containers. 

Create `~/compose.yaml` and paste the following (`nano ~/compose.yaml`). This is the Docker compose stack that runs
all the *arrs and download clients.

```yaml
services:
  jackett:
    image: lscr.io/linuxserver/jackett:latest
    container_name: jackett
    environment:
      - PUID=1000
      - PGID=1005
      - UMASK=002
      - TZ=Australia/Brisbane
    volumes:
      - /media-data/config-jackett:/config
      - /media-data:/data
    ports:
      - 9117:9117
    restart: unless-stopped
    networks:
      - arrs
  sonarr:
    image: lscr.io/linuxserver/sonarr:latest
    container_name: sonarr
    environment:
      - PUID=1000
      - PGID=1005
      - UMASK=002
      - TZ=Australia/Brisbane
    volumes:
      - /media-data/config-sonarr:/config
      - /media-data:/data
    ports:
      - 8989:8989
    restart: unless-stopped
    networks:
      - arrs
  radarr:
    image: lscr.io/linuxserver/radarr:latest
    container_name: radarr
    environment:
      - PUID=1000
      - PGID=1005
      - UMASK=002
      - TZ=Australia/Brisbane
    volumes:
      - /media-data/config-radarr:/config
      - /media-data:/data
    ports:
      - 7878:7878
    restart: unless-stopped
    networks:
      - arrs
  sabnzbd:
    image: lscr.io/linuxserver/sabnzbd:latest
    container_name: sabnzbd
    environment:
      - PUID=1000
      - PGID=1005
      - UMASK=002
      - TZ=Australia/Brisbane
    volumes:
      - /media-data/config-sabnzbd:/config
      - /media-data:/data
    ports:
      - 8080:8080
    restart: unless-stopped
    networks:
      - arrs
  transmission:
    image: lscr.io/linuxserver/transmission:latest
    container_name: transmission
    environment:
      - PUID=1000
      - PGID=1005
      - UMASK=002
      - TZ=Australia/Brisbane
      - USER=admin
      - PASS=GENERATE-A-PASSWORD-TO-LOGIN
    volumes:
      - /media-data/config-transmission:/config
      - /media-data:/data
    ports:
      - 9091:9091
      - 51413:51413
      - 51413:51413/udp
    restart: unless-stopped
    networks:
      - arrs
  unpackerr:
    image: golift/unpackerr
    volumes:
      - /media-data:/data
    user: 1000:1005
    environment:
      - TZ=Australia/Brisbane
      - UN_QUIET=false
      - UN_DEBUG=false
      - UN_ERROR_STDERR=false
      - UN_LOG_QUEUES=1m
      - UN_LOG_FILES=10
      - UN_LOG_FILE_MB=10
      - UN_INTERVAL=2m
      - UN_START_DELAY=1m
      - UN_RETRY_DELAY=5m
      - UN_MAX_RETRIES=3
      - UN_PARALLEL=1
      - UN_FILE_MODE=0644
      - UN_DIR_MODE=0755
      - UN_ACTIVITY=false
      - UN_SONARR_0_URL=http://sonarr:8989
      - UN_SONARR_0_API_KEY=PUT-SONARR-API-KEY-HERE
      - UN_RADARR_0_URL=http://radarr:7878
      - UN_RADARR_0_API_KEY=PUT-RADARR-API-KEY-HERE
    restart: unless-stopped
    networks:
      - arrs
networks:
  arrs: null

```

Bring the whole stack up:

```bash
cd ~ && docker compose up -d
```

The `-d` just detaches it from your terminal — it isn't what makes the stack survive a reboot. That comes from
`restart: unless-stopped` on every service, plus Docker's own service being enabled at boot (`sudo systemctl enable docker`).

### Point the apps at the right paths
Everything lives under `/data` inside the containers, so use these paths when you first configure each app:

| App          | Setting                                           | Path                         |
|--------------|---------------------------------------------------|------------------------------|
| Sonarr       | Media Management > Root Folder                    | `/data/tv`                   |
| Radarr       | Media Management > Root Folder                    | `/data/movies`               |
| SABnzbd      | Folders (tab) > Temporary Download Folder         | `/data/downloads/incomplete` |
| SABnzbd      | Folders (tab) > Completed Download Folder         | `/data/downloads/complete`   |
| Transmission | Edit Preferences > Download to                    | `/data/downloads`            |
| Transmission | Edit Preferences > Uncheck "Use temporary folder" |                              |

Unpackerr needs the API keys from Sonarr and Radarr, found under **Settings → General → API Key** in each app.
Drop them into the `UN_SONARR_0_API_KEY` and `UN_RADARR_0_API_KEY` placeholders above and run `docker compose up -d`
again — it'll restart in a loop until they're valid.

Transmission needs a password set to use as the web UI login. Set `PASS` to set the UI password.
